2. MODERN LOCATOR PRIORITY & STRICT MODE SAFETY (CRITICAL)
═══════════════════════════════════════════════════════════════════════════════
CRITICAL UNIQUENESS & SAFETY RULE: Playwright throws "strict mode" errors if an 
action (click, fill) targets an element locator that has multiple entries in the DOM. 
To prevent functional tests from crashing, you MUST make locators as unique as 
possible. Furthermore, as a mandatory safety fallback, ALWAYS append `.first()` 
to EVERY locator before performing an action or assertion.

ALWAYS prefer user-facing locators. CSS selectors are a last resort.

TIER 1 (Accessibility-first):
  - page.getByRole('button', { name: 'Submit' }).first()
  - page.getByRole('link', { name: 'Profile' }).first()
  - page.getByRole('checkbox', { name: 'Remember me' }).first()
  - page.getByRole('heading', { level: 1 }).first()
  - page.getByRole('combobox').first() — for selects/dropdowns

TIER 2 (Form-specific):
  - page.getByLabel('Email Address').first()
  - page.getByPlaceholder('Enter search term').first()
  - page.getByAltText('Product image').first()

TIER 3 (Content-based):
  - page.getByText('Exact text', { exact: true }).first()
  - page.getByText('Partial', { exact: false }).first()

TIER 4 (Element attributes):
  - page.locator('[data-testid="submit-btn"]').first()
  - page.locator('[name="email"]').first()
  - page.locator('#header-logo').first()

DO NOT fall back to bare CSS selectors (.class-name, div > p) unless absolutely
necessary, and only if the element has no accessible attributes.

3. WORKFLOW DESIGN — REALISTIC USER JOURNEYS
═══════════════════════════════════════════════════════════════════════════════
Analyze page metadata (title, URL, heading, description) to infer the PRIMARY
BUSINESS INTENT. Then construct a coherent, multi-step user journey that:

   - If dropdown exists: open it, select option, verify selection reflected.

4. ASSERTION STRATEGY — OUTCOME VERIFICATION (MANDATORY)
═══════════════════════════════════════════════════════════════════════════════
Tests MUST verify that the workflow succeeded. Use MULTIPLE assertions targeting
different aspects of the outcome:

TYPE A — State Change Assertion (Most Important):
  After a primary action, verify the UI changed in a way that proves success:
  - await expect(page.getByRole('heading', { name: 'Results' }).first()).toBeVisible();
  - await expect(page.locator('[data-testid="success-message"]').first()).toContainText('Order placed');
  - await expect(page.getByRole('link', { name: 'My Orders' }).first()).toBeVisible();

TYPE B — URL/Navigation Assertion:
  Verify the page navigated to expected route:
  - await expect(page).toHaveURL(/\/dashboard/);
  - expect(page.url()).toContain('order-confirmed');

TYPE C — Element Count/Existence Assertion:
  Verify expected number of results, items, or form fields:
  - await expect(page.locator('[data-testid="result-item"]')).toHaveCount(5);

TYPE D — Text/Content Assertion:
  Verify expected text appears (not just visibility):
  - await expect(page.getByRole('status').first()).toContainText('Success');
  - await expect(page.getByText(/Order/).first()).toBeVisible();

TYPE E — Form/Input State Assertion:
  Verify form state after submission:
  - await expect(page.getByPlaceholder('Email').first()).toHaveValue('');
  - await expect(page.getByRole('button', { name: 'Submit' }).first()).toBeDisabled();

PICK 1-3 COMPLEMENTARY ASSERTIONS that together prove the workflow succeeded.
